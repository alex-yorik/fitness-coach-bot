# ARCHITECTURE.md

Архитектура проекта `fitness-coach-bot`. Живой документ — обновляется в том же PR,
что и код, который он описывает (правило синхронизации из внутреннего стандарта
качества (не публикуется), раздел «Документация — живая, не разовая»).

## Обзор

Проект состоит из двух сервисов, которые запускаются из одного Docker-образа
и разделяют единую SQLite-базу через общий volume `./data`:

| Сервис | Контейнер | Команда | Порт | Назначение |
|---|---|---|---|---|
| Telegram-бот | `fitness-coach` | `python -m app.bot` | 8001 (health) | приём заявок, визитка, CRM в Telegram |
| Веб-админка | `fitness-coach-webadmin` | `python -m admin.web` | 5004 | просмотр/смена статусов, выгрузка Excel |

Оба сервиса описаны в `docker-compose.yml` и имеют `healthcheck`.

### Путь заявки на пробную тренировку

1. Пользователь нажимает кнопку пробной тренировки (или шлёт текст кнопки).
2. `MessageHandler` из entry_points `ConversationHandler` (`app/handlers/trial.py`)
   запускает `trial_start` — состояние `NAME`.
3. Шаги `NAME → AGE → GOAL → CONTACT` проходят последовательно; каждый ответ
   валидируется через `validate_answer()` (`app/validators.py`), при ошибке —
   повторный запрос с тем же состоянием. Кнопки «◀️ Назад» (`back_step`) и
   «❌ Отменить» (`cancel`) — fallbacks диалога.
4. На последнем шаге `_save_application()` пишет строку в таблицу `applications`
   и уведомляет администратора в Telegram (`ADMIN_CHAT_ID`).
5. Администратор работает с заявками либо в Telegram (CRM-команды `/crm`,
   `/all`, `/stats`), либо в веб-админке на порту 5004.

## Хранилище (SQLite)

- Файл БД: `DATABASE_PATH` (по умолчанию `/app/data/database.db`), монтируется
  в оба контейнера.
- Схема — одна таблица `applications`:
  `id`, `created_at`, `name`, `age`, `goal`, `contact`, `status`
  (статус добавлен миграцией `ALTER TABLE` в `init_db()`).
- `PRAGMA journal_mode=WAL` + `busy_timeout=5000` (`app/database.py`) позволяют
  боту, админке и health-серверу работать с одним файлом: читатели не блокируют
  друг друга, писатели сериализуются через таймаут.
- Резервное копирование — `scripts/backup.sh` через атомарный `sqlite3 backup`
  API, ротация 14 дней, доступ `0600`.

**Почему SQLite, а не отдельный СУБД-сервер:** объём данных — сотни заявок,
нагрузка — один тренер. SQLite — zero-ops, один файл, транзакционная
целостность и лёгкое бэкапирование. Для текущего сценария отдельный сервер
PostgreSQL/MySQL — избыточность (см. `TECH_DEBT.md` — прямой SQL без ORM).

## Ключевые решения

### Почему `ConversationHandler` для формы записи

Форма — многошаговый диалог (имя → возраст → цель → контакт) с промежуточной
валидацией и возвратом на предыдущий шаг. `ConversationHandler` из
python-telegram-bot:

- хранит состояние диалога в `context.user_data` (изолировано по чату/пользователю);
- `entry_points` / `states` / `fallbacks` задают граф переходов декларативно;
- шаги не нужно хранить в БД или куках — состояние живёт в памяти процесса,
  что достаточно для single-instance бота;
- fallbacks покрывают «назад» и «отменить» без ручной маршрутизации сообщений.

Альтернатива (полный FSM в БД или один огромный `MessageHandler` с ручными
проверками) была бы избыточной и менее читаемой.

### Почему Flask для админки

- Админка — небольшой CRUD поверх одной таблицы с авторизацией: Flask даёт это
  в одном файле (`admin/web.py`) без генераторов проекта и шаблонных «толстых»
  фреймворков.
- Экосистема: `flask-limiter` (rate-limit на логин), встроенная session-авторизация,
  `openpyxl` для выгрузки Excel.
- Джанго был бы оправдан при десятках моделей и отдельном админ-API; здесь это
  лишний вес. Flask-приложение запускается как второй контейнер из того же образа,
  разделяя БД и код конфигурации.

### Почему контент в JSON, а не в коде

Все тексты бота (визитка, шаги формы, кнопки) лежат в `content/fitness_coach.json`.
`app/content_loader.py` загружает его с кэшем по mtime и валидирует структуру
(`app/validators.py::validate_content`). Это позволяет менять тексты без
пересборки образа и без деплоя кода (достаточно перезапуска контейнера).

### Почему два контейнера из одного образа

Бот и админка имеют разные жизненные циклы (рестарт бота при смене контента не
должен ронять админку) и разные health-проверки. Общий образ экономит место и
упрощает версионирование зависимостей (`requirements.txt` один на проект).

## Наблюдаемость

- `app/health_server.py` — HTTP-сервер `GET /healthz` (порт 8001): проверяет
  доступность БД, отвечает `200 ok` / `503 database unavailable`. Используется
  `healthcheck` в docker-compose.
- `app/logging_config.py` — `RotatingFileHandler` (10 МБ × 5 файлов) в `/app/logs`
  (volume `./logs`), отдельный файл для веб-админки (`WEB_LOG_PATH`).

## Тесты

Unit-тесты в `tests/unit/` покрывают валидаторы, БД, хендлеры, health-сервер,
логирование и Flask-админку. Live-тесты Telegram API помечены `@pytest.mark.live`
и в обычном прогоне не выполняются. См. `README.md` → «Тесты».
